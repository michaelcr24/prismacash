Plan de implementación · documento v1.0

PrismaCash

Pulseras y códigos QR contactless para ferias, picnics y eventos: recarga en el quiosco, cobro en cada punto de venta, saldo verificado y registrado en tiempo real.

React + Vite + Tailwind Supabase (Postgres · RLS · Realtime) Vercel PWA · NFC / QR Expo (Fase 2)
01 · quiosco

Recarga

El asistente compra un dispositivo; el operador lo activa y carga un monto X en su wallet.

02 · punto de venta

Pago

Se escanea NFC o QR según el evento, se verifica saldo y estado, se descuenta y se registra.

03 · autogestión

Reembolso / bloqueo

Saldo no usado se reembolsa; un dispositivo extraviado se bloquea y se reemplaza sin perder historial.

01

Resumen ejecutivo

Sistema SaaS multi‑evento: los organizadores venden pulseras/llaveros NFC o códigos QR a los asistentes, recargan saldo en un quiosco y cobran en N puntos de venta escaneando el dispositivo — todo con dashboard en tiempo real y roles por sucursal.

Decisiones de producto cerradas

  • Multi‑tenancy: un único proyecto Supabase compartido por todos los eventos/clientes que alquilen el servicio, aislado por event_id vía RLS — no un proyecto por cliente.
  • Naturaleza del saldo: crédito cerrado de uso interno del evento, no dinero electrónico transferible — detalle en sección 06.
  • App móvil nativa: Fase 2, después de validar el MVP web en un evento real.
  • Cronograma: guía flexible de secuencia de trabajo para un desarrollador, sin fecha de evento piloto comprometida.
02

Alcance por fases

El MVP cubre el ciclo operativo completo de un evento. Todo lo que depende de un piloto real validado se empuja a fases posteriores.

  • Registro y configuración de eventos (solo super_admin): nombre, paleta, logo, tipo de dispositivo (NFC o QR).
  • Gestión de sucursales/terminales: quiosco de recarga + N puntos de venta.
  • Usuarios y roles: super_admin, event_admin, operator asignado a su sucursal.
  • Registro de asistente + asignación de dispositivo (ID único) + recarga inicial.
  • Cobro: escaneo → verificación → débito → registro de transacción.
  • Bloqueo de dispositivo extraviado + reasignación con migración de saldo.
  • Dashboard en tiempo real: ventas, transacciones, saldo circulante, terminales activas.
  • Historial de transacciones (id, fecha/hora, sucursal, monto, tipo).
  • App móvil (Expo): autogestión de saldo, historial, solicitud de reembolso.
  • Reportes exportables (CSV / Excel / PDF).
  • Recarga online con pasarela (Stripe, Mercado Pago o institución bancaria) desde la app.
  • Modo offline tolerante en puntos de venta: cola local + sincronización idempotente.
  • Múltiples eventos simultáneos con aislamiento total de datos.
  • Analítica avanzada: heatmaps de consumo por hora / terminal / producto.
  • API pública y webhooks para integraciones externas.
  • Kioscos en modo pantalla completa bloqueada (kiosk mode).
03

Arquitectura

Supabase como backend único: Postgres con RLS resuelve el multi‑tenant, las Edge Functions son la única puerta de entrada para mutar saldo. Vercel solo construye y sirve el frontend — nunca toca el dinero.

04

Modelo de datos

Postgres sobre Supabase. El saldo vive separado de la identidad (wallets vs devices/attendees) y el ledger de transacciones nunca se edita ni se borra.

Ver esquema SQL completo
schema.sql
-- ══ multitenant ══ organizations -- tenant raíz (tu empresa, arrienda el servicio) id, name, slug, plan, created_at events -- cada feria / picnic / evento id, org_id → organizations, name, slug, status (draft|active|closed), device_type (nfc|qr|hybrid), brand_primary, brand_secondary, logo_url, currency, max_balance, refund_policy (jsonb), starts_at, ends_at -- ══ ubicaciones y usuarios ══ branches -- "sucursales": quiosco de recarga, chinamos, puntos de venta id, event_id → events, name, type (recharge_kiosk|sales_point|both), is_active terminals -- dispositivo físico dentro de una sucursal id, branch_id → branches, device_label, last_seen_at, is_active profiles -- extiende auth.users id → auth.users, org_id, full_name, phone, role (super_admin|event_admin|operator) branch_members -- asignación usuario ↔ sucursal (rota por turno) id, user_id → profiles, branch_id → branches, assigned_at -- ══ dispositivos y saldos ══ devices -- pulsera / llavero NFC o código QR id, event_id → events, uid (único: ID NFC / contenido QR), type (nfc|qr), status (unassigned|active|blocked|retired), assigned_profile_id → attendees, replaced_by → devices wallets -- una por dispositivo — separa saldo de identidad id, device_id → devices (unique), balance numeric(12,2), version int -- concurrencia optimista, updated_at attendees -- persona registrada en el quiosco id, event_id, full_name, phone, email, document_id -- ══ transacciones — append-only, nunca se edita ni se borra ══ transactions id uuid pk, event_id, branch_id, terminal_id, device_id, type (initial_load|topup|payment|refund|migration_out|migration_in|adjustment), amount numeric(12,2), balance_before, balance_after, attendant_id → profiles, metadata jsonb, created_at refund_requests -- solicitudes desde la app móvil id, device_id, amount, status (pending|approved|rejected|paid), requested_by, processed_by, processed_at

Reglas de integridad

  • devices.uid único por evento; nunca se reutiliza.
  • wallets.balance solo se muta dentro de una Edge Function.
  • transactions es append-only — UPDATE/DELETE revocado por RLS.

Índices críticos

  • (event_id, created_at desc)
  • (device_id, created_at desc)
  • (branch_id, created_at)
05

Lógica transaccional atómica

Toda mutación de saldo corre en una Edge Function con pg_advisory_xact_lock(device_id), para que dos terminales cobrando al mismo dispositivo a la vez nunca produzcan saldo negativo. Objetivo de rendimiento: < 300 ms por cobro.

issue-device · quiosco de recarga

  • Valida rol y pertenencia a la sucursal.
  • Crea/actualiza attendee, crea devices + wallets(balance=0).
  • Ejecuta initial_load en la misma transacción y devuelve {device_uid, balance}.

block-and-replace · dispositivo extraviado

  • Bloquea el dispositivo viejo (status=blocked) en la misma transacción.
  • Crea el nuevo y migra el saldo con migration_out / migration_in.
  • El historial del asistente queda íntegro — nada se pierde.
06

Encuadre legal del saldo

⚠ Crédito cerrado, no dinero electrónico

El saldo cargado en un dispositivo es un crédito cerrado de uso interno del evento — no es dinero electrónico ni un instrumento de pago transferible. Evita que el sistema deba tratarse como un emisor regulado (en Costa Rica, actividad supervisada por la SUGEF) y sigue el estándar de la industria de festivales con pulseras cashless cerradas.

  • No es retirable a terceros: no se transfiere entre dispositivos ni a cuentas bancarias o billeteras de terceros — solo se consume en el evento o se reembolsa a quien lo cargó.
  • Reembolso = devolución del saldo no consumido, no un pago. En el MVP se entrega en efectivo o revirtiendo el medio de pago original, en el propio quiosco — sin retiro bancario ni transferencia P2P.
  • Términos aceptados en la recarga inicial: checkbox o firma en tablet declarando que el saldo es un crédito de uso exclusivo del evento, no transferible, reembolsable según política — texto a validar con asesoría legal antes de operar a escala.
  • refund_policy (jsonb) debe fijar ventana de reembolso, montos mínimo/máximo y comisión administrativa si aplica.
  • Ofrecer recarga online + reembolso bancario (posible extensión de la app móvil) acerca el saldo a un instrumento de dinero electrónico y exige revisión legal previa — no se construye sin validar ese punto primero.
07

Seguridad y roles

Row Level Security de Supabase con claims de evento en el JWT. El alcance se estrecha en cada nivel — nadie ve más de lo que su rol necesita.

super_admin
Organizaciones, eventos, branding — lectura total entre eventos
event_admin
Sucursales, terminales y usuarios dentro de su evento; aprueba reembolsos; cierra el evento
operator
Solo su terminal/sucursal: issue-device, charge, block-and-replace
attendee
Solo su propio dispositivo, saldo e historial — vía app móvil

Implementación

  • Toda tabla lleva event_id; política RLS lee claims del JWT (custom_access_token_hook: org_id, event_id, role).
  • Los operadores nunca consultan saldo libre — las funciones de cobro devuelven solo lo necesario.

Endurecimiento

  • Rate limiting en Edge Functions.
  • terminal_id validado contra el usuario autenticado.
  • Tests automáticos de aislamiento entre eventos en CI.
08

Frontend PWA

Prioridad número uno: velocidad en el punto de venta. Todo lo demás — branding, dashboard, rutas — se organiza alrededor de eso.

UX del punto de venta

  1. 1Pantalla en espera de escaneo (cámara / NFC activo).
  2. 2Escaneo automático → tarjeta con nombre, saldo, últimos 3 consumos.
  3. 3Teclado numérico gigante + botón "COBRAR" a pantalla completa.
  4. 4Feedback triple: vibración, sonido, flash verde/rojo.

NFC / QR en la PWA

Web NFC (NDEFReader) solo existe en Android/Chrome — las terminales iOS operan en modo QR con html5-qrcode. El evento se configura como nfc, qr o hybrid, y la terminal activa el lector correspondiente.

Branding dinámico: al cargar /e/:eventSlug se inyectan --brand-primary / --brand-secondary, logo y theme-color desde la config del evento.

10

Escalabilidad y concurrencia

Garantías

  • pg_advisory_xact_lock + UPDATE ... WHERE balance ≥ amount: jamás hay saldo negativo aunque N terminales cobren al mismo dispositivo a la vez.
  • Idempotencia por client_tx_id (uuid generado en la terminal) — un reintento de red nunca duplica el cobro.
  • El dashboard suscribe solo INSERT de transacciones de su evento, filtrado en Postgres Changes.

Capacidad

  • Supabase Pro/Team con read replicas y pooler de conexiones para eventos masivos.
  • Estimado MVP: 2.000–5.000 tx/hora sin fricción; arquitectura preparada para 10×.
  • Fase 2: cola offline en IndexedDB con resolución de conflictos por client_tx_id.
